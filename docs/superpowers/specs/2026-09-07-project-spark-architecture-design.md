# Project Spark 架构设计

## 1. 目标与范围

Project
Spark 是一套服务于单个公司、单个微信公众号的营销活动系统。运营人员从开发人员提供的完整活动模板中选择一种，填写模板开放的配置并发布活动。系统首版只提供“展会抽奖”模板，完成微信识别、关注检测、留资、抽奖、现场兑奖和线索导出闭环。

模板可以在代码内部组合微信身份、钉钉表单接入、抽奖、答题、投票、奖励和核销等能力，但运营后台只展示一个完整模板，不提供流程拖拽或组件编排。后续由开发人员增加签到、答题、投票和游戏等模板。

首版按 MVP 范围实施，不以一周为硬性上线期限。首版包含一个完整活动模板和固定角色权限；更多模板、概率编辑、复杂库存、可配置 RBAC 和 BI 在真实活动验证后逐步增加。留资表单由钉钉维护，不计划自建表单设计器。

本设计为当前实施依据。原始 MVP、V1 业务需求和微信流程文档作为业务背景；其中自建表单、无条件 100% 中奖、库存及过期统计与本设计不一致的部分，以本设计的已确认规则为准。

## 2. 总体架构

项目采用单仓库和模块化单体。四个应用独立构建，通过同一域名的路径发布：

```text
apps/
├─ activity/    /activity/:activityCode
├─ staff/       /staff
├─ admin/       /admin
└─ api/         /api
```

- `activity`：所有活动模板的用户运行入口。根据活动编码加载已发布的模板版本和配置。
- `staff`：稳定的工作人员平台，负责登录、选择活动、扫码和确认核销。
- `admin`：运营管理后台，负责活动创建、模板选择、配置、发布、数据查看和导出。
- `api`：统一服务端，承载微信接入、钉钉回调、身份、活动、参与、抽奖、库存、核销和导出等业务。

网关将 `/activity/*`、`/staff/*`、`/admin/*` 和 `/api/*`
分别转发到对应应用。三个前端配置各自的路由和静态资源基础路径。活动 URL 不包含模板类型，避免模板实现泄漏到外部链接。

`activityCode`
由系统生成，是 URL 安全、全局唯一且发布后不可变的短编码。活动开始前可通过发布新版本修改名称，外部二维码和渠道链接始终使用稳定编码。

## 3. 技术栈

仓库使用 pnpm
workspace 和 Turborepo。三个前端使用 React、TypeScript、Vite、React
Router、TanStack Query、React Hook Form、Zod、Radix UI 和 Tailwind
CSS。服务端使用 NestJS 和 Fastify，数据存储使用 PostgreSQL 和 TypeORM。测试使用 Vitest 与 Playwright。

系统不使用 Redis。活动用户、工作人员和管理员的服务端 Session 存入 PostgreSQL，并使用不同的 Cookie 名称和会话类型。Cookie 设置
`HttpOnly`、`Secure` 和合适的 `SameSite`
属性。数据库是参与状态、中奖结果、库存和核销记录的唯一事实来源。

## 4. 共享包

首版只建立确有跨应用共享价值的包：

```text
packages/
├─ contracts/
└─ templates/
```

`contracts` 按
`auth`、`activities`、`participants`、`prizes`、`lottery`、`redemptions`、`staff`
和 `exports` 组织，保存 API 请求与响应类型、枚举、错误码和共享 Zod
Schema。它不包含数据库实体、权限判断或业务处理逻辑。

`templates` 保存模板注册信息、配置结构、配置版本、默认值和校验规则。首版包含
`exhibition-lottery`。它不包含 React 页面、后台配置界面或服务端抽奖逻辑；这些实现分别位于使用它们的应用中。

`contracts` 可以引用 `templates` 导出的配置类型；`templates` 不依赖
`contracts`。四个应用可以同时依赖这两个包。

Radix UI 由各前端直接使用。各应用在自己的 `components` 和 `styles`
中封装界面，不建立共享 UI 包。ESLint 和 TypeScript 公共配置保存在仓库根目录。数据库 Schema、迁移和种子数据位于
`apps/api/database`。

`activity` 与 `staff`
必须在业务页面实现前交付可审阅的 UI 设计稿，包含高保真页面、交互流程和异常状态；经用户确认后作为实现和视觉验收基准。`admin`
无需独立 UI 设计稿，按功能需求、Radix
UI 和统一界面规范直接实现。设计规范可以共享颜色、字号和间距约定，但不因此新增共享 UI 包。

## 5. 模板模型

运营可见的模板是一套完整活动方案。一个模板定义：

- 稳定的模板标识与显示名称；
- 配置 Schema、默认值和配置版本；
- 固定的参与流程；
- 活动端实现、后台配置实现和服务端处理器；
- 可输出的统计和导出字段。

首版模板标识为 `exhibition-lottery`。共享定义位于
`packages/templates/src/exhibition-lottery`；活动页面位于
`apps/activity/src/templates/exhibition-lottery`；运营配置界面位于
`apps/admin/src/templates/exhibition-lottery`；服务端流程适配位于
`apps/api/src/templates/exhibition-lottery`。

每个活动绑定明确的模板版本。发布时生成不可变配置快照；后续修改模板或草稿不会改变正在运行或已经结束的活动。新建活动默认使用模板最新版。模板配置只描述允许运营修改的内容，库存扣减、参与限制、抽奖和核销规则始终由服务端执行。

注册表使用 `(templateId, templateVersion)`
精确解析，各端保留仍被活动引用的实现。部署前检查数据库中已发布版本均被候选版本支持，不支持则阻止部署；仅保存版本字符串不等于保存历史行为。

首版在活动开始前允许发布新版本，以修订号校验防止覆盖他人的编辑。活动首次开始后锁定模板、钉钉表单绑定、字段映射、主图、名称、奖项和时间规则。仅允许管理员提前结束抽奖、为已有奖项增加库存、管理工作人员权限；不得减少库存、删除奖项或重开已结束活动。通用奖品库后续编辑不改变活动奖品快照，中奖时再保存奖项、名称、图片和兑奖截止时间快照。运行中的库存计数独立于发布配置维护。

## 6. 服务端模块

`apps/api/src` 使用具体业务名称划分模块：

```text
auth/           管理员、工作人员和活动用户会话
wechat/         静默 OAuth、OpenID 映射和关注检测
activities/     活动、模板版本、配置快照和发布
participants/   用户活动关系、参与状态和留资
dingtalk/       表单回调校验、提交关联和数据同步
lottery/        抽奖资格、随机选择和防重复抽奖
prizes/         奖品、活动库存和库存变更
redemptions/    兑奖码、兑奖状态和核销事务
staff/          工作人员账号和活动权限
reports/        基础活动指标
exports/        Excel 线索导出
media/          活动及奖品图片上传
jobs/           PostgreSQL 持久化任务、重试与清理
health/         存活和数据库就绪检查
templates/      完整活动模板对上述模块的编排
```

模块在同一 NestJS 应用和数据库内运行，通过明确的服务接口协作。首版不拆微服务，也不建立动态插件加载系统。

## 7. 核心数据模型

核心实体包括：

- `WechatIdentity`、`User`、`Session`：微信公众号身份和三类会话；
- `Activity`、`ActivityVersion`：活动本体、草稿版本和不可变的发布快照；
- `ActivityParticipation`：用户在某活动中的公共参与状态，主键 `participationId`
  使用随机 UUID，并设置 `(activityId, userId)` 唯一约束；
- `DingTalkFormSubmission`：钉钉表单提交标识、关联信息和留资数据快照；
- `WebhookReceipt`、`BackgroundJob`：已接收的回调及可重试任务；
- `Prize`、`ActivityPrize`：奖品资料和活动库存；
- `LotteryRecord`：一次正式抽奖结果；
- `Redemption`：安全兑奖码、状态、有效期和核销信息；
- `AdminAccount`、`StaffAccount`、`StaffActivityPermission`：管理员、工作人员及可核销活动；
- `ChannelVisit`：活动渠道和访问归因。
- `StockAdjustment`、`AuditEvent`、`MediaAsset`、`ExportJob`：补库存、关键操作审计、图片和导出任务。

模板清单由代码注册表维护，不单独建立模板数据库表。`ActivityVersion`
保存模板标识、模板版本、配置 Schema 版本、配置 JSONB 和版本状态；`Activity`
保存当前草稿版本及已发布版本的引用。

通用字段使用明确的数据库列。不同模板之间差异较大的配置和结果扩展可以使用 JSONB，但需要由带版本的 Zod
Schema 校验。抽奖、库存和核销等需要查询、约束或事务处理的数据使用独立关系表。

## 8. 用户流程与接口

用户访问
`/activity/:activityCode?channel=:channelCode`。活动端请求已发布活动；没有活动 Session 时跳转
`/api/wechat/oauth/start`。OAuth 回调验证签名后的
`state`，用 OpenID 查找或创建内部用户，创建 PostgreSQL
Session，并返回原活动地址。

需要留资时，服务端根据当前微信 Session 创建或读取该用户在当前活动的参与记录，使用钉钉支持的 URL 预填格式，将其
`participationId`
填入钉钉多维表格表单的“参与编号”字段。链接由服务端生成，不接受客户端指定其他用户的参与编号。用户再次进入同一活动时复用原记录；不另外建立签名关联令牌或令牌表。

用户已确认钉钉支持 URL 预填并保存字段，自动化支持自定义请求头、引用记录 ID 和表单字段。运营配置表单提交触发的自动化 HTTP 请求，将参与编号、记录 ID 和留资字段发送至 Spark。字段隐藏或只读能力作为可选设置，不作为安全保证；具体 URL 预填语法在接入联调时验证。

系统不自建留资表单结构、填写界面或前端字段校验。模板配置保存钉钉表单标识、访问地址、参与编号预填映射和留资字段映射。服务端仍校验回调数据结构、字段类型和必要数据。回调密钥通过服务端配置提供，不进入公开模板配置或表单 URL。

自动化请求使用 HTTPS，接口约定如下。`formId`
是自动化中固定配置的绑定表单标识，`recordId` 和其他值引用钉钉记录。

```http
POST /api/integrations/dingtalk/form-submissions
Authorization: Bearer <回调密钥>
Content-Type: application/json
```

```json
{
  "formId": "bound-form-id",
  "recordId": "dingtalk-record-id",
  "participationId": "29e1d85a-6bd3-4bdc-8c2b-40867e5731c6",
  "fields": {
    "name": "示例姓名",
    "phone": "示例手机号"
  }
}
```

用户返回活动页或重新扫码后，通过自己的微信 Session 查询参与状态；留资引导页提供“我已提交，检查状态”入口。等待回调时进行有上限的轮询，超时提示稍后重试，不自动视为留资完成，也不依赖钉钉自动跳回活动页。

活动模板根据服务端返回的参与状态展示关注、留资引导、抽奖、奖品或已兑奖页面。刷新、退出和重新扫码都从数据库恢复状态。模板前端只发送动作，服务端决定动作是否合法以及下一状态。

API 按调用方划分：

```text
/api/activity/*   活动用户接口
/api/wechat/*     OAuth 与公众号接口
/api/integrations/dingtalk/*  钉钉表单回调接口
/api/staff/*      工作人员接口
/api/admin/*      运营管理接口
```

所有状态变更接口支持幂等处理并返回稳定的业务错误码。活动不存在、未发布、未开始、已结束、配置损坏和微信接口失败均有明确页面或重试策略。

## 9. 一致性与安全

钉钉自动化回调使用请求头中的共享密钥鉴权，不假设存在钉钉官方事件签名、时间戳或重试保证。服务端校验密钥、请求结构、参与记录存在性，以及记录所属活动绑定的表单是否与
`formId`
一致。无效鉴权返回 401，数据格式错误返回 400，不匹配的参与记录或表单拒绝处理；均不得更新留资和资格。

回调分接收和业务处理两步。鉴权和校验通过后，在一个事务中保存 `WebhookReceipt`
与唯一任务，持久化成功才返回 200。返回 200 表示可靠接收，不代表资格已生效；数据库不可用返回 503，不能假装成功。`WebhookReceipt`
和 `DingTalkFormSubmission` 均以 `(formId, recordId)`
去重；相同记录携带不同参与编号返回 409，相同参与编号的重复通知返回 200，保留第一次接收的载荷。

任务处理在事务中锁定参与记录，保存提交快照并标记留资完成。多个记录关联同一个参与编号时，按该参与记录的回调接收顺序处理，保留首次有效留资结果；其他记录保留来源但不覆盖线索、不增加资格。自动化只绑定新增提交，不把后续记录编辑作为重新发资格事件。首版不提供人工修改已确认线索的入口。

任务以 PostgreSQL 行锁、租约和退避时间领取，支持崩溃后回收；最多执行 5 次，重试间隔为 10 秒、30 秒、2 分钟和 10 分钟，耗尽后显示失败原因并允许管理员重放同一任务。重放仍经过全部校验。服务端从未收到的回调无法靠内部重试恢复，部署手册说明在钉钉侧检查自动化执行记录并重发；不假设平台自动重试。活动结束后的合法回调仍保存线索，但不能恢复抽奖资格。抽奖接口另外检查关注状态、活动规则和既有中奖记录。

`participationId`
只用于表单关联，不能登录、查询他人的留资或中奖信息、执行抽奖或核销。用户接口仍以微信 Session 校验记录归属；工作人员接口仍校验登录身份和活动权限。回调密钥不写入日志，不向前端返回。

抽奖在一个 PostgreSQL 事务内锁定参与记录，校验资格，通过带条件的库存更新或行锁防止超卖，创建唯一中奖记录并更新参与状态。数据库设置用户与活动唯一中奖约束。

核销事务锁定兑奖记录，校验状态、有效期和工作人员活动权限，然后一次性写入核销人员与时间。两个工作人员同时扫码时只有一个事务能够成功。

兑奖码使用不可预测的安全随机值，保存检索哈希及加密后的原值，服务端仅向中奖记录所属用户恢复二维码。管理员与工作人员密码使用安全密码哈希。公众号密钥、回调共享密钥、Cookie 密钥、兑奖码加密密钥和数据库凭据通过环境变量或部署密钥注入；只有实际调用钉钉 API 时才要求钉钉应用凭据。手机号和其他线索数据只在授权的后台和导出范围内返回，核销端默认仅显示奖项、兑奖状态和必要的脱敏身份信息。

首版暂不实现请求限流；与业务正确性相关的重复提交仍由 PostgreSQL 约束和事务处理。Session 清理使用数据库定时任务或应用维护任务。后续确认限流需求时，再根据部署规模选择网关或应用层实现。

## 10. 验证与交付顺序

第一阶段建立工作区、四个应用、共享包、数据库迁移和基础 CI。第二阶段打通微信 OAuth、PostgreSQL
Session、活动查询与发布快照。第三阶段打通钉钉表单跳转、回调关联、留资同步和资格更新。第四阶段完成抽奖、库存、兑奖和工作人员核销闭环。第五阶段完成后台活动、奖品、用户、工作人员和 Excel 导出，并在真实微信与钉钉环境中进行端到端和现场并发验收。

工程和接口工作可与 UI 设计并行推进；用户活动端及工作人员端的业务页面实现分别依赖各自设计稿确认。活动端覆盖活动首页、关注引导、钉钉留资跳转、回调等待、抽奖、奖品二维码，以及未开始、已结束、库存耗尽、已核销、已过期和网络失败状态。工作人员端覆盖登录、活动选择、工作台、扫码及备用输入、奖品核对、确认核销、核销结果，以及无权限、会话过期、无效码、已核销、过期和网络中断状态。

设计交付保存于 `docs/design/activity/` 和
`docs/design/staff/`，至少包含可浏览的高保真原型、主要页面截图和设计说明。活动端强调品牌呈现、参与引导和二维码可读性；工作人员端强调单手操作、状态辨识和防误发奖。以 390
px 宽移动端为主要画板，检查 320、375、430
px 宽度的布局及移动端安全区；实现阶段与已确认稿进行截图对照。钉钉表单本身由外部平台维护，仅设计跳转前后界面。

测试重点包括无效回调密钥、重复与乱序回调、不存在或跨活动的参与编号、重复填写不重复发资格、参与编号不能越权查询或抽奖、钉钉回调延迟及事务失败后重发、并发抽奖最后一份库存、重复抽奖返回原结果、两个工作人员同时核销、Session 丢失后重新扫码、活动时间边界、外部接口失败以及发布后修改草稿不影响线上活动。首版完成标准是核心闭环在真实公众号、钉钉表单和移动设备上稳定运行。

## 11. 已确认业务边界（问题 2～5）

### 11.1 库存与中奖承诺

采用“有库存时，每次有效抽奖必中奖”。留资完成不预留库存；库存耗尽返回
`OUT_OF_STOCK`，不生成中奖记录、不消耗一次资格，活动仍进行且补库存后可重试。库存不足时停止引导新用户为抽奖填写资料，提示奖品已抽完；已经跳转钉钉的用户仍可提交并保存线索。活动规则需提前说明数量有限及先到先得。

抽奖按各活动奖项的剩余可抽数量加权随机。首版在事务内串行锁定同一活动的奖池行，统一锁顺序为活动奖池、参与记录、奖项；管理员补库存走同一奖池锁。依次执行已有结果查询、时间和资格校验、库存选择、扣减、中奖与兑奖记录写入。重复抽奖即使发生在活动结束后，也返回原有结果。不同活动可独立执行；不预设高并发吞吐保证，以真实 PostgreSQL 压测确认容量。

### 11.2 生命周期、过期与统计

活动配置
`startAt`、`drawEndAt`、`endAt`、`redeemEndAt`：分别表示活动开始、停止新抽奖、活动页结束和兑奖截止。发布时要求
`startAt < drawEndAt <= endAt <= redeemEndAt`。数据库保存带时区时间，以服务端 UTC 时钟判定，运营界面按 Asia/Shanghai 展示。有效区间采用起点包含、终点不包含；人工提前结束只停止新抽奖，不改变活动页结束和兑奖截止时间。

已中奖用户即使取消关注或活动结束，也可查看原结果并在兑奖截止前核销。没有中奖记录的用户到达抽奖截止时间后不能抽奖；已核销结果优先于过期显示。兑奖接口实时判断截止时间，不依赖清理任务。过期奖品不自动返还奖池，首版不支持延期、撤销核销或重新发奖。

库存统计：剩余可抽 = 总投入 − 已中奖；已中奖 = 待兑奖 + 已核销 + 已过期。已过期只统计尚未核销且已到截止时间的记录。活动奖池与现场实物剩余是不同指标，不混用。访问人数按用户与活动去重；已确认关注人数表示曾经成功确认关注的参与人数，不宣称是公众号净增关注数；来源归因采用首次有效渠道，重新扫码不覆盖。

### 11.3 发布与回调规则

问题 3 采用第 5 节的版本锁定、活动奖品快照及兼容性检查；问题 4 采用第 9 节的首次有效留资、可靠接收、持久化任务和人工重放规则。上述选择均已获用户同意，不再作为待确认项。

## 12. 身份、现场使用与运维补充

- 管理员通过一次性初始化命令创建，无默认生产密码、无公开注册；工作人员由管理员创建。角色固定为管理员和工作人员，工作人员必须有对应活动权限。禁用或重置密码立即撤销现有会话，每次请求检查账号状态。
- 会话使用随机不透明标识，数据库保存哈希、角色和绝对过期时间。活动用户会话 7 天，管理员及工作人员 8 小时；登录后轮换标识，退出立即删除。生产 Cookie 使用
  `Secure`、`HttpOnly`、`SameSite=Lax`
  和 host-only 域。三个 Cookie 使用不同名称。浏览器写请求校验 Origin 及绑定会话的 CSRF
  token；外部回调使用独立密钥鉴权，不依赖 Cookie。
- 微信 OAuth `state`
  除签名外绑定浏览器 nonce，在 PostgreSQL 中保存一次性记录，10 分钟过期，原子消费；返回地址只允许本系统活动路径。微信调用发生在抽奖事务之外，关注校验失败关闭新抽奖入口并允许重试；关注成功缓存最长 60 秒。微信 access
  token 由 PostgreSQL 共享，刷新使用数据库锁协调。
- 核销二维码指向
  `/staff/redeem/:code`；可用微信扫一扫打开工作人员页并在登录后恢复核销位置，也可使用平台内相机扫描。拒绝相机权限时允许粘贴或手工输入兑奖码。扫码只查询，工作人员核对奖品后点击确认才核销；网络中断后重查状态，禁止盲目重复发实物。兑奖码页面设置无外部引用和
  `Referrer-Policy: no-referrer`，日志脱敏。
- 首版管理员上传 JPEG、PNG、WebP 图片，单张不超过 5
  MB，校验真实文件类型与尺寸，使用随机文件名；不接收 SVG。图片存储在部署持久卷，经同域
  `/media/*`
  只读提供。生产首版单 API 实例；数据库和媒体卷独立持久化。将来扩容需替换媒体存储适配器，无需移动业务模块到共享包。
- 导出由管理员按活动发起 PostgreSQL 任务，分批读取首次有效留资及中奖、兑奖、渠道数据，生成 XLSX；用户输入按文本写入，避免公式执行。下载重新鉴权，文件 24 小时过期。记录导出人、活动、时间和结果；联系方式仅用于授权业务，日志不输出完整回调载荷、密钥或个人信息。
- 数据库迁移独立于应用启动执行，生产禁用 TypeORM 自动同步。提供
  `/api/health/live` 和
  `/api/health/ready`；后者检查数据库。网关设置请求体上限，API 返回统一错误码和请求编号；请求限流留待后续设计。
- 部署手册包含 HTTPS、公众号域名配置、钉钉自动化映射、秘密配置、版本兼容检查、迁移、备份与恢复步骤。上线前实际演练恢复 PostgreSQL、图片卷和兑奖码加密密钥。备份每日执行，保留 7 天并限制访问；恢复演练记录耗时与可恢复数据时间点，不宣称零数据丢失。
- 关键审计覆盖发布、提前结束、补库存、核销、权限变化、任务重放和导出；提供最小失败任务列表，不建设通用日志中心。真实微信扫码、外部表单预填和回调的联调必须留有脱敏证据，Mock 通过不等于外部联调完成。
