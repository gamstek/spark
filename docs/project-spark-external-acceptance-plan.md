# Project Spark 外部联调验收计划

对应[上线验收](project-spark-acceptance.md)中「外部联调」一节的 6 项未完成检查。当前生产活动使用匿名身份；本计划以可分享的活动链接和浏览器 Cookie 会话为准，不把公众号关注、服务器回调或 OAuth 作为当前验收前提。每项通过后回填上线验收文档对应 checkbox。

## 一、前置条件（联调资源准备）

| 资源     | 要求                                                                                    | 用途                   |
| -------- | --------------------------------------------------------------------------------------- | ---------------------- |
| 测试活动 | 管理后台创建并发布 `exhibition-lottery` 活动，配置奖品、主图与活动规则                  | 全流程                 |
| 分享链接 | 可访问 `https://spark.gamstek.com/activity/<activityCode>`，且活动页面可深链接刷新      | 匿名活动会话           |
| 测试设备 | 一台普通浏览器、一台微信内浏览器；另备无痕窗口或第二台设备                              | 分享链接与 Cookie 边界 |
| 生产配置 | API 容器收到 `ACTIVITY_IDENTITY_MODE=anonymous`；数据库已从空库重建，活动和自有表单可用 | 全部                   |

`wechat`
身份模式及保留的 OAuth 流程仅供未来具备该能力的公众号账户使用，不属于当前匿名生产验收。若未来启用，须另行制定并批准该模式的联调计划，不能把其结果作为本计划的通过条件。

## 二、验收项与测试用例

### 1. 可分享活动链接建立匿名 Session

实现：activity H5 初始读取 runtime/info 无会话时，调用
`POST /api/activity/:code/session`；匿名模式返回 `authenticated: true` 并建立
`spark_activity` Cookie，随后 H5 刷新 runtime/info。

| #   | 步骤                                    | 预期                                                                      |
| --- | --------------------------------------- | ------------------------------------------------------------------------- |
| 1.1 | 在普通浏览器首次打开 `/activity/<code>` | 自动建立匿名会话并进入已发布活动；runtime/info 可读取，不要求在微信中打开 |
| 1.2 | 在微信内首次打开同一分享链接            | 同样建立匿名会话并进入活动                                                |
| 1.3 | 观察首次打开的浏览器网络记录            | 不跳转 OAuth 授权页；bootstrap 返回 `authenticated: true` 后刷新活动数据  |

### 2. 匿名 Cookie 的 7 天边界

实现：匿名 session 使用 `spark_activity`
Cookie，`HttpOnly`、`SameSite=Lax`，最长保存 7 天；生产环境另有 `Secure` 属性。

| #   | 步骤                                            | 预期                                                                                              |
| --- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| 2.1 | 检查首次访问后的响应和浏览器 Cookie             | Cookie 的 `Max-Age` 为 604800（7 天），且具有 `HttpOnly` 与 `SameSite=Lax`；生产部署具有 `Secure` |
| 2.2 | 在同一浏览器保留 Cookie 后重新打开分享链接      | 恢复同一匿名会话；已创建的参与记录继续关联该会话                                                  |
| 2.3 | 清除 Cookie、使用无痕窗口或在另一台设备打开链接 | 建立新的匿名会话和参与记录；运营方已确认这不是跨设备的同一人去重能力                              |

### 3. 活动页内填写固定报名表

实现：匿名会话在 FORM 状态直接显示 13 题表单，调用
`POST /api/activity/:code/form-submissions`。无需离开活动页；答案与留资状态在一个事务中保存。

| #   | 步骤                           | 预期                                                             |
| --- | ------------------------------ | ---------------------------------------------------------------- |
| 3.1 | 打开活动并进入表单             | Q1–Q13 按顺序显示，Q1–Q12 必填，Q13 可选；手机号和邮箱不限制格式 |
| 3.2 | 选择两个“其他”选项后提交空说明 | 对应说明处提示必填，取消选择后不提交隐藏说明                     |
| 3.3 | 未勾选隐私同意时提交           | 前后端均拒绝，服务端不写答案、不确认留资                         |
| 3.4 | 填完必填项并同意隐私协议       | 提交成功，刷新 runtime 进入 LOTTERY；后台详情显示完整 13 题      |
| 3.5 | 刷新页面或遇到网络失败         | 同一活动会话可恢复草稿；失败内容保留，可重试                     |

### 4. 提交鉴权、事务与重复请求

| #   | 步骤                           | 预期                                                                           |
| --- | ------------------------------ | ------------------------------------------------------------------------------ |
| 4.1 | 无活动会话提交                 | 401，数据库不写报名记录                                                        |
| 4.2 | 有会话但无效 CSRF 提交         | 拒绝请求，不写答案或留资状态                                                   |
| 4.3 | 同一会话重复或并发提交有效表单 | 仅一条报名记录，始终保留首次答案                                               |
| 4.4 | 模拟提交事务中途失败           | 答案与留资状态一起回滚，重试后完整保存                                         |
| 4.5 | 未提交者在抽奖截止后提交       | 拒绝首次提交；已提交者重试不修改原答案                                         |
| 4.6 | 在后台查看详情并生成 XLSX      | 展示 13 题、两个条件说明、多选中文标签及留资时间；表格逐列导出，手机号保留文本 |
| 4.7 | 响应丢失后重试                 | 返回已提交状态，答案与总数不变                                                 |

### 5. 提交后抽奖，并发不超发

实现：`POST /api/activity/:code/lottery`（CSRF + 原子库存扣减）；并发原子性已由
`lottery.integration.test.ts`
覆盖，此处做真实环境复核。匿名模式不检查公众号关注状态。

| #   | 步骤                                | 预期                                                         |
| --- | ----------------------------------- | ------------------------------------------------------------ |
| 5.1 | 已完成留资的匿名会话点“立即抽奖”    | 出奖 → 中奖页 → 兑奖页显示真实兑奖码与可扫二维码             |
| 5.2 | 同一浏览器会话重复抽奖              | 幂等返回同一结果，不重复扣库存                               |
| 5.3 | 两台真实手机对最后 1 份库存并发抽奖 | 恰好 1 人中奖；另一人收 `OUT_OF_STOCK`，页面提示“奖品已抽完” |
| 5.4 | 未留资状态抽奖                      | 400 `LEAD_REQUIRED`，前端回到表单步骤                        |
| 5.5 | 抽奖结束后再抽                      | 已中奖者返回原结果；未中奖者 409 `ACTIVITY_ENDED`            |

### 6. 工作人员扫码核销

实现：staff H5 扫码（BarcodeDetector）/ 手动输码 →
`POST /api/staff/redemptions/lookup` → 确认 →
`POST /api/staff/redemptions/confirm`（CSRF，幂等）。

| #   | 步骤                           | 预期                                                          |
| --- | ------------------------------ | ------------------------------------------------------------- |
| 6.1 | 用户出示兑奖二维码，职员扫码   | 识别兑奖码 → 确认页显示奖品、脱敏参与人、`WAIT_REDEEM`        |
| 6.2 | 核对后点“确认发放”             | 成功页显示真实核销时间与核销人员；用户端奖品页状态变“已核销”  |
| 6.3 | 确认请求丢响应后再次扫描同一码 | lookup 返回原 `REDEEMED` 结果（幂等），确认页显示“已完成核销” |
| 6.4 | 扫描已过期兑奖码               | 410 `REDEMPTION_EXPIRED`，确认页显示过期、无法发放            |
| 6.5 | 扫描无权限活动或随机的兑奖码   | 404 `REDEMPTION_NOT_FOUND`，提示“兑奖码无效”                  |
| 6.6 | 相机权限被拒或浏览器不支持扫码 | 提示改用手动输入，输码流程可完成核销                          |

## 三、故障与现场演练

对应上线验收「故障与现场操作」：

- **匿名重复参与风险演练**：按用例 2.3 在另一设备建立新会话，确认现场人员与运营方理解该行为符合匿名限制，不能当作缺陷或跨设备防刷措施。
- **缺货演练**：库存清零后活动页停在“奖品已抽完”；确认管理后台只能通过“添加库存”恢复，不允许其他方式改库存。
- **重复提交演练**：用例 4.3/4.7；演练前后核对中奖、库存、核销总数一致。
- **误发实物演练**：确认审计记录（活动、兑奖码、工作人员、时间）完整，由运营按记录人工处理，不直接修改中奖记录。

## 四、执行顺序与通过标准

1. 准备第一节资源并确认 API 容器中的 `ACTIVITY_IDENTITY_MODE=anonymous`；
2. 按顺序执行：项 1（分享链接）→ 项 2（Cookie 边界）→ 项 3（表单）→ 项 4（提交安全与幂等）→ 项 5（抽奖并发）→ 项 6（核销）；
3. 执行第三节故障演练。

每项通过标准：留档真实证据（录屏或截图 + 管理后台/数据库截图），并回填[上线验收](project-spark-acceptance.md)对应 checkbox。任一用例失败时记录接口错误码与响应中的
`requestId`，用于日志定位，再决定修复或重试。
